# Переговорная — бронирование комнаты

Интерфейс бронирования переговорной комнаты на рабочий день **09:00–18:00**: выбор даты, просмотр броней,
создание, редактирование и удаление. Формат отображения — вертикальный таймлайн дня.

## Как запустить

Нужен **Node.js 24 LTS** (версия зафиксирована в `.node-version`; с fnm/nvm достаточно `fnm use` / `nvm use`).

```bash
npm install
npm run dev          # http://localhost:3000
```

Остальные команды:

```bash
npm test             # unit- и компонентные тесты (Vitest)
npm run lint         # ESLint
npm run typecheck    # TypeScript, strict
npm run build && npm start   # production-сборка
```

Данные хранятся в памяти сервера и при первом запросе заполняются демо-бронями на сегодня и завтра.
После перезапуска сервера данные сбрасываются.

## Стек

- **Next.js 16** (App Router), **React 19**, **TypeScript 6** в strict-режиме.
- **CSS Modules** — без UI-библиотек и state-менеджеров: состояние организовано средствами React.
- **Mock API** — Next.js Route Handlers + in-memory store.
- **Vitest** + React Testing Library.

## Что сделано

### Интерфейс

- Выбор даты, расписание выбранного дня, кнопка «Создать бронирование».
- Таймлайн 09:00–18:00 в точном масштабе: брони показаны с временем начала, окончания и названием,
  свободное время — штриховкой с подписью «Свободно». Соседние брони (`10:00–11:00` и `11:00–12:00`) разделены
  видимой границей. Время не привязано к получасовым слотам: `10:15–11:00` допустимо.
- Одна форма для создания и редактирования: дата, начало, окончание, необязательное название.
  При изменении начала окончание сдвигается с сохранением длительности; текущая длительность видна в форме.
- Удаление — с подтверждением; запись исчезает из расписания только после успешного ответа сервера.
- Состояния: загрузка, пустой день, ошибка загрузки с кнопкой «Повторить», отправка формы (кнопка заблокирована,
  повторная отправка невозможна), ошибки валидации у полей, ошибки сохранения и удаления.
- Результаты операций — toast-уведомления, которые не сдвигают раскладку и исчезают через 5 секунд.
- Адаптивная вёрстка; на мобильных кнопки действий переносятся под описание брони.
- Доступность: семантическая разметка, подписи связаны с полями, ошибки текстом (не только цветом),
  видимый фокус, модальные окна на нативном `<dialog>` (фокус внутри окна, закрытие по Esc, возврат фокуса).

### Бизнес-правила

Правила реализованы чистыми функциями в `src/lib/booking/rules.ts` и проверяются **и на клиенте, и на сервере**
(клиент — для удобства, сервер — обязательная защита).

| Правило из ТЗ | Как реализовано |
|---|---|
| Начало и конец внутри рабочего дня | `09:00 ≤ start`, `end ≤ 18:00` |
| `start < end` | отдельная ошибка у поля «Окончание» |
| Длительность 30 минут – 2 часа | границы включительно: 30 и 120 минут допустимы |
| Брони не пересекаются, касание допустимо | полуоткрытые интервалы: `newStart < existingEnd && newEnd > existingStart` |
| Нельзя бронировать прошедшие даты | ошибка валидации; кнопка «Создать» на прошедших датах неактивна с пояснением |
| Для сегодня прошедшее время недоступно | начало не раньше текущей минуты; прошедшее свободное время не показывается как свободное; у начавшихся броней нет кнопки «Изменить» |
| Бронь не конфликтует сама с собой | при редактировании текущая бронь исключается из проверки по `id` |
| Сервер может вернуть `409` | см. ниже |

**Обработка `409`.** Форма остаётся открытой со всеми введёнными значениями, показывается сообщение
«Это время уже занято. Расписание обновлено — выберите другое время», расписание перезагружается,
пользователь может изменить время и отправить снова.

Сравнение с «сейчас» идёт по **локальному времени пользователя**: клиент передаёт свой часовой пояс
в заголовке `X-Timezone`, сервер считает текущие дату и время по нему (а не по часовому поясу сервера).
Даты и время передаются строками `YYYY-MM-DD` / `HH:mm`, для вычислений переводятся в минуты от начала суток —
без неявных преобразований в UTC.

### Mock API

| Метод | Путь | Успех |
|---|---|---|
| `GET` | `/api/bookings?date=YYYY-MM-DD` | `200 { bookings }` |
| `POST` | `/api/bookings` | `201 { booking }` |
| `PATCH` | `/api/bookings/:id` | `200 { booking }` |
| `DELETE` | `/api/bookings/:id` | `204` |

Ошибки в едином формате `{ "error": { "code", "message", "fieldErrors?" } }`:
`400` — некорректный запрос, `404` — бронь не найдена, `409` — пересечение, `422` — нарушение бизнес-правил,
`412` — бронь изменилась с момента загрузки (защита от одновременного редактирования через `If-Match`).

Проверка пересечения и запись выполняются в одной синхронной операции над хранилищем, поэтому между ними
не может вклиниться другой запрос. Хранилище индексировано по дате.

### Разделение API и UI

```
src/
  app/                      страница, layout, Route Handlers
  components/               BookingApp, BookingForm, Schedule, Modal, ConfirmDeleteDialog, Toast
  hooks/                    useBookings, useLocalNow
  lib/
    api/bookingsClient.ts   API-клиент: запросы, разбор ответов, типизированные ошибки
    booking/                типы, бизнес-правила, расписание, значения формы, версия брони
    time.ts                 работа с датами и временем
  server/                   хранилище, сервис, HTTP-маппинг
```

- Компоненты не вызывают `fetch` и не разбирают HTTP-ответы — только методы `bookingsApi` и `ApiError`.
  Чтобы подключить реальный бэкенд, достаточно заменить `src/lib/api/bookingsClient.ts`.
- Серверный сервис возвращает доменный результат и не знает про HTTP; статусы выставляются в Route Handlers.
- После успешной операции ответ сервера применяется к локальному состоянию без повторной загрузки дня;
  полная перезагрузка — только когда данные заведомо устарели (`409`, `412`, `404`).

### Тесты

`npm test` — 70 тестов:

- бизнес-правила: минимальная и максимальная длительность, меньше 30 и больше 120 минут, `start < end`,
  выход за рабочие часы, пересечения, касание границ, исключение текущей брони, прошедшая дата,
  прошедшее время сегодня;
- работа с временем и часовыми поясами, построение расписания, сдвиг окончания в форме;
- хранилище и Route Handlers: статусы `200/201/204/400/404/409/412/422` и формат ошибок;
- компонент: при `409` форма сохраняет данные и расписание обновляется; успешное создание применяется
  без повторной загрузки; у прошедших броней нет кнопки «Изменить».

## Что не сделано

Намеренно вне скоупа ТЗ, в порядке приоритета доработки:

1. **Постоянное хранилище.** Сейчас данные живут в памяти одного процесса: сбрасываются при перезапуске,
   а на serverless-хостинге (в т. ч. Vercel) разные инстансы могут видеть разные данные. Следующий шаг —
   БД с ограничением на пересечение на уровне базы (например, `EXCLUDE USING gist` в Postgres).
2. **Обновления в реальном времени** (SSE или периодический опрос). Сейчас устаревшее расписание обнаруживается
   при сохранении (`409` / `412`) и сразу обновляется.
3. **E2E-тесты** (Playwright) для клавиатурной навигации, фокуса в модальных окнах и мобильной вёрстки.
4. **Клиентский кеш** между датами (SWR / React Query) — сейчас при возврате на дату данные загружаются заново.
5. **Быстрая навигация по дням** («Сегодня», предыдущий / следующий день) — по ТЗ требуется только выбор даты.
6. **Несколько комнат** — в ТЗ одна переговорная, поэтому в модели нет `roomId`.
7. **Авторизация и владелец брони** — ТЗ прямо исключает.
8. **Тёмная тема.**
