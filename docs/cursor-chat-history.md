# ТЗ: Приложение для бронирования переговорной комнаты

## 1. Создание приложения и технологический стек

Создай веб-приложение для бронирования переговорной комнаты со следующим стеком:

- **Next.js** — App Router.
- **React**.
- **TypeScript** в строгом режиме.
- **CSS Modules** для стилизации.
- **Vitest** для unit-тестирования бизнес-логики.
- **React Testing Library** для тестирования React-компонентов, если потребуются компонентные тесты.
- **Next.js Route Handlers** для реализации mock API.
- **In-memory store** для хранения бронирований без подключения базы данных.

Не используй Tailwind CSS. UI-библиотеки и библиотеки управления состоянием добавляй только при наличии обоснованной необходимости.

Перед установкой зависимостей проверь существующее окружение и структуру проекта. Если приложение уже создано, адаптируй его под требования, не перезаписывая существующий код без необходимости.

Настрой TypeScript в строгом режиме. Обеспечь возможность запуска приложения в режиме разработки, выполнения тестов и создания production build.

## 2. Назначение приложения

Приложение предназначено для бронирования одной переговорной комнаты в течение рабочего дня.

Рабочие часы: 09:00–18:00.

Пользователь должен иметь возможность:

- выбирать дату;
- просматривать существующие бронирования на выбранную дату;
- видеть время начала и окончания каждой брони;
- создавать бронирования;
- редактировать существующие бронирования;
- удалять бронирования.

Интерфейс должен быть простым, понятным и адаптивным. Основной приоритет — корректная бизнес-логика, предсказуемое поведение и качественная обработка ошибок.

## 3. Интерфейс и пользовательский сценарий

### 3.1. Главный экран

На главном экране должны отображаться:

- заголовок «Переговорная»;
- элемент выбора даты;
- кнопка «Создать бронирование»;
- расписание выбранного дня с 09:00 до 18:00;
- существующие бронирования.

После выбора другой даты приложение должно загрузить и отобразить бронирования для неё.

### 3.2. Отображение расписания

Используй вертикальный таймлайн или другую простую визуализацию, которая позволяет быстро различать занятое и свободное время.

Требования:

- Отображать временную шкалу от 09:00 до 18:00.
- Показывать существующие бронирования на соответствующих временных промежутках.
- Для каждого бронирования отображать время начала, время окончания и название, если оно задано.
- Визуально различать занятые и свободные промежутки.
- Показывать точные границы бронирований.
- Корректно отображать соседние бронирования, границы которых соприкасаются.
- Не использовать фиксированные получасовые слоты как обязательные единицы выбора времени.
- Не генерировать автоматически рекомендации или готовые интервалы бронирования.

Пользователь самостоятельно выбирает время начала и окончания в форме, ориентируясь на расписание.

### 3.3. Создание и редактирование

Используй одну форму для создания и редактирования бронирования.

Поля формы:

- дата;
- время начала;
- время окончания;
- название встречи — необязательное поле.

При создании форма должна открываться с разумными начальными значениями.

При редактировании поля должны заполняться данными выбранной брони.

Форма должна обеспечивать:

- валидацию введённых значений;
- понятное отображение ошибок;
- индикацию отправки запроса;
- предотвращение повторной отправки;
- сохранение введённых значений при ошибках API;
- закрытие формы после успешного сохранения.

### 3.4. Удаление

Перед удалением бронирования запрашивать подтверждение.

После успешного удаления обновлять расписание. При ошибке показывать понятное сообщение и не создавать ложного впечатления, что запись удалена.

## 4. Модель данных

Используй следующий тип:

```typescript
type Booking = {
  id: string;
  date: string; // YYYY-MM-DD
  start: string; // HH:mm
  end: string; // HH:mm
  title?: string;
};
```

Дата и время должны передаваться через API в указанных форматах.

Не использовать объекты `Date` как формат хранения или передачи данных API. Преобразовывать значения во внутреннее представление только там, где это необходимо для сравнений и вычислений.

## 5. Бизнес-правила и валидация

Реализуй все правила на клиенте и на сервере. Клиентская валидация предназначена для удобства пользователя, серверная является обязательной защитой целостности данных.

### Ограничения времени

1. Рабочий день: 09:00–18:00 включительно по границам интервала.
2. Время начала должно быть строго меньше времени окончания.
3. Минимальная длительность бронирования — 30 минут.
4. Максимальная длительность бронирования — 120 минут.
5. Бронирование не должно выходить за пределы рабочего дня.
6. Время может начинаться не только на границе получаса. Например, 10:15–11:00 допустимо.

### Пересечения

Бронирования одной комнаты не могут пересекаться.

Соприкосновение границ допустимо: бронирования 10:00–11:00 и 11:00–12:00 могут существовать одновременно.

Используй проверку пересечения полуоткрытых интервалов:

```typescript
newStart < existingEnd && newEnd > existingStart
```

При редактировании необходимо исключать текущую бронь из проверки пересечений по её `id`.

### Ограничения по дате и текущему времени

- Запрещено создавать бронирования на прошедшие даты.
- Для сегодняшней даты запрещено бронирование, время начала которого уже прошло.
- При редактировании также проверять допустимость даты и времени.
- Сравнивать дату и время с текущими локальными датой и временем пользователя.
- Не допускать ошибок из-за неявного преобразования даты в UTC или несовпадения часовых поясов.

Для вычислений удобно преобразовывать время в количество минут от начала суток.

## 6. Mock API

Реализуй API с использованием Next.js Route Handlers.

Необходимые endpoints:

- `GET /api/bookings?date=YYYY-MM-DD` — получить бронирования на дату.
- `POST /api/bookings` — создать бронирование.
- `PATCH /api/bookings/:id` — изменить бронирование.
- `DELETE /api/bookings/:id` — удалить бронирование.

Используй in-memory store с начальными демонстрационными данными.

Требования к API:

- Проверять входные данные и бизнес-правила на сервере.
- Возвращать HTTP 409 при конфликте бронирований.
- Возвращать корректные HTTP-статусы при ошибках валидации, отсутствии записи и успешных операциях.
- Использовать единообразный формат ошибок.
- Исключить текущую запись при проверке пересечений во время редактирования.
- Выполнять проверку пересечений и запись последовательно в рамках одной операции над хранилищем.
- Инициализировать демонстрационные данные предсказуемо, не добавляя их повторно при каждом запросе.

Хранилище не обязано сохранять данные после перезапуска сервера. Это ограничение должно быть совместимо с архитектурой приложения.

## 7. Разделение API и UI

Изолируй сетевой слой от компонентов интерфейса.

Создай отдельный API-клиент, который отвечает за:

- выполнение запросов;
- преобразование ответов;
- обработку HTTP-ошибок;
- предоставление типизированного интерфейса для UI.

Компоненты не должны самостоятельно формировать HTTP-запросы или разбирать детали HTTP-ответов.

Серверную бизнес-логику и функции валидации вынеси в отдельные модули, не связанные с React.

Избегай избыточных абстракций и не добавляй глобальный state manager, если состояние приложения можно понятно организовать средствами React.

## 8. Обработка состояний и ошибок

Реализуй следующие состояния интерфейса:

- загрузка бронирований;
- успешная загрузка;
- отсутствие бронирований на выбранную дату;
- ошибка загрузки;
- отправка формы;
- ошибки валидации;
- ошибка создания или редактирования;
- конфликт бронирований;
- ошибка удаления.

При ошибке загрузки предоставлять пользователю возможность повторить запрос.

Не использовать только цвет для обозначения ошибок. Сообщения должны быть понятными и не раскрывать внутренние технические детали.

### Обработка HTTP 409

Если сервер возвращает конфликт при создании или редактировании бронирования:

1. Показать сообщение: «Это время уже занято. Расписание обновлено — выберите другое время».
2. Сохранить все введённые значения формы.
3. Повторно загрузить бронирования выбранной даты.
4. Обновить расписание.
5. Оставить форму открытой.
6. Позволить пользователю изменить данные и повторить запрос.

Не сбрасывать форму и не считать операцию успешной.

## 9. Тестирование

С помощью Vitest покрой тестами критичную бизнес-логику:

- допустимая минимальная длительность;
- допустимая максимальная длительность;
- длительность меньше 30 минут;
- длительность больше 120 минут;
- начало раньше окончания;
- выход за рабочие часы;
- пересечение бронирований;
- допустимое соприкосновение границ;
- исключение текущей брони при редактировании;
- бронирование на прошедшую дату;
- бронирование с прошедшим временем начала на сегодняшнюю дату.

Дополнительно проверь корректность ответа API при конфликте и сохранение данных формы при HTTP 409.

## 10. Адаптивность и доступность

- Обеспечить видимый фокус интерактивных элементов.
- Если используется модальное окно, корректно управлять фокусом и закрытием.

## 11. Структура и качество кода

Поддерживать понятное разделение ответственности между:

- страницами и UI-компонентами;
- формой бронирования;
- визуализацией расписания;

Реализуй все правила на клиенте и на сервере. Клиентская валидация предназначена для удобства пользователя, серверная является обязательной защитой целостности данных.

### Ограничения времени

1. Рабочий день: 09:00–18:00 включительно по границам интервала.
2. Время начала должно быть строго меньше времени окончания.
3. Минимальная длительность бронирования — 30 минут.
4. Максимальная длительность бронирования — 120 минут.
5. Бронирование не должно выходить за пределы рабочего дня.
6. Время может начинаться не только на границе получаса. Например, 10:15–11:00 допустимо.

### Пересечения

Бронирования одной комнаты не могут пересекаться.

Соприкосновение границ допустимо: бронирования 10:00–11:00 и 11:00–12:00 могут существовать одновременно.

Используй проверку пересечения полуоткрытых интервалов:

```typescript
newStart < existingEnd && newEnd > existingStart
```

При редактировании необходимо исключать текущую бронь из проверки пересечений по её `id`.

### Ограничения по дате и текущему времени

- Запрещено создавать бронирования на прошедшие даты.
- Для сегодняшней даты запрещено бронирование, время начала которого уже прошло.
- При редактировании также проверять допустимость даты и времени.
- Сравнивать дату и время с текущими локальными датой и временем пользователя.
- Не допускать ошибок из-за неявного преобразования даты в UTC или несовпадения часовых поясов.

Для вычислений удобно преобразовывать время в количество минут от начала суток.

## Архитектура

**Что хорошо:**
- **Слои разделены чисто.** Чистая логика без React лежит в `src/lib`, сервер — в `src/server`, сетевой слой — в `bookingsClient`, состояние — в хуке `useBookings`, отображение — в компонентах. Тестировать каждый слой можно отдельно.
- **Правила записаны в одном месте.** `validateBooking` и `findConflict` используют и клиент, и сервер, дублирования проверок нет.
- **Время хранится строками** и переводится в минуты только для вычислений, календарная арифметика идёт в UTC. Поэтому ошибок со сдвигом суток нет, и тест это проверяет.
- **Внешних зависимостей минимум:** нет zod, менеджера состояния и UI-библиотек.

**Слабые места:**
1. **Сервисный слой возвращает `Response`.** `bookingService` смешивает бизнес-логику с HTTP, и переиспользовать его, например в Server Actions, нельзя. Правильнее отдавать доменный результат (`ok`, `conflict`, `not_found`, `validation`), а статусы проставлять в route handler.
2. **Атомарность держится на синхронности.** Проверка пересечения и запись не перемешиваются только потому, что JS однопоточный, а методы store синхронные. С настоящей БД методы станут асинхронными, и эта гарантия пропадёт. Понадобится ограничение в самой базе, например в Postgres `EXCLUDE USING gist` по диапазону времени, или транзакция с блокировкой. Интерфейс store сейчас синхронный, так что миграция затронет сигнатуры.
3. **Нет контроля одновременных правок.** Если двое редактируют одну бронь, сохранится последняя запись без предупреждения. Не хватает версии записи или ETag с ответом 409 или 412.
4. **Опорное «сейчас» вызывает сомнения.** ТЗ требует сравнивать с локальным временем пользователя, поэтому клиент шлёт заголовок `X-Timezone`. Но этот заголовок можно подделать. И у физической комнаты есть свой часовой пояс, который логичнее брать за источник истины. Кроме того, демо-данные создаются по дате сервера, а не пользователя.
5. **Модель рассчитана на одну комнату.** `roomId` нет ни в модели, ни в API, а это первое, что понадобится при росте.
6. **Нет авторизации и владельца брони:** любой может удалить что угодно. Для mock это допустимо, но архитектура для этого места пока не готова.
7. **Не настроен линтер.** Кроме того, TypeScript 7 очень свежий: часть инструментов, например typescript-eslint, может его ещё не поддерживать.

## Оптимизация и производительность

Для текущего объёма узких мест нет. Есть несколько мест, которые станут проблемой при росте:
- **`listByDate` перебирает и сортирует все записи** при каждом GET и при каждой проверке конфликта. Хватит индекса вида `Map<date, Booking[]>`, а в БД — индекса по `(room_id, date)`.
- **После каждой мутации идёт лишний GET** всего дня, хотя ответ POST или PATCH уже содержит запись. Это просто и гарантирует согласованность, но при частых операциях можно сливать ответ в локальное состояние, а полную перезагрузку оставить для 409.

- Бандл маленький, мемоизация не нужна: пересчёт сегментов на 5–10 бронях ничего не стоит.

## Масштабируемость

Решение не масштабируется горизонтально, но для mock это ожидаемо:
- **Хранилище на `globalThis`** живёт только в одном процессе. На serverless или нескольких инстансах у каждого будут свои данные.
- **Нет обновлений в реальном времени.** Другой пользователь видит устаревшее расписание, пока не получит 409. Это обработано корректно, но опыт хуже, чем с SSE или периодическим опросом.

Путь к продакшену понятный: асинхронный репозиторий, ограничение в БД, `roomId`, версия записи, авторизация. Слои под это готовы, переписывать придётся в основном сервис и store.
